# Ops tickets

For a ticket whose ledger says `kind: ops` (SKILL.md, stage B): no `.py` file changes, only CI,
a Dockerfile or compose file, a configuration or environment file, a dependency pin, a shell
script or docs. The stages run as SKILL.md writes them except where this page says otherwise.
A code ticket that also changes such a file uses this page's check for it (*The verification
plan*, *A dependency pin*) and nothing else here.

## B. The drawing

Draw the path from the changed file to its effect: which pipeline job, image, container or
running service reads it, and when.

## E. The verification plan

The failing test becomes a **verification plan**, written in `tasks.md` before the change:
the commands whose output the change must alter, what each prints today, and what it should
print after (a setting's value read back, the jobs of the MR's pipeline and their result). A
docs-only change is verified by reading each changed claim against the code it describes.

A check that prints the same before and after shows only that nothing broke: it is the task's
gate, and the repository's Python gate joins it only where the change can reach it (tool
configuration in `pyproject.toml`, a file the tests read).

- A pipeline file: `rtk proxy glab ci lint <checkout>/.gitlab-ci.yml -R <group>/<repo>`, one
  line for any valid file, the reason and exit 1 otherwise.
- A compose file: `docker compose -f <file> config -q`. It starts nothing and needs no lock;
  without `-q` it prints `.env`'s values.
- An image: the pipeline job that builds it proves it. No local `docker build`.

He predicts before each run, as with a test, and each result goes under its line in
`tasks.md` as it runs.

## E. A dependency pin

After the constraint is edited (*Who writes what*):

- Where the repository tracks its lock (rest-api, central-backend), you run `poetry lock` from
  `<checkout>`; in a linked worktree it leaves an empty `.venv`, which you remove. At G the
  lock is one hunk, `generated by poetry lock` in `understanding.md`: he names the packages
  that moved and why.
- Where the lock is git-ignored (syneto-diana, syneto-mercurio), nothing is regenerated: the
  constraint is the whole change.

Nothing is installed into `<repo>/.venv`, which every other branch and worktree of the
repository runs on, so the local gate still tests the old version: the proof is the MR
pipeline's test job.

## E. Who writes what

The pen table's *Failing test* row says who writes the plan, and its *Production code* row who
makes the change. His prompt names the plan's check where the prompt pattern asks for a test
id, and the file's neighbours where it asks for house skills. From Level 2 it goes to a
general-purpose agent with the coder's brief lines (`reviewing-generated-code.md`), since the
Python implementor writes Python tests.

## E. Checks that wait

A check that needs a pipeline waits for stage I's pipeline watch; when the watch ends, read
the plan's pipeline lines against the pipeline's jobs with him and update the MR's section. A
check that needs a change in the deploy repo, or a cluster, is not his: the MR says what
Cristian has to verify.

## F. Review

There is no Python guard or reviewer. The checklist's Python rules give way to the
repository's own conventions for that file: its other jobs, its other Dockerfiles.
